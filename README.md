# E1-3 Mini NPU 시뮬레이터

패턴(N×N)과 필터를 MAC(Multiply-Accumulate) 연산으로 비교해 십자(Cross)와 X 중 어느 모양인지 판정하는 간단한 NPU 시뮬레이터입니다.
Python 3.8 이상, 표준 라이브러리만 사용합니다(NumPy 등 외부 라이브러리 없음).

## 실행 방법

```bash
python3 main.py
```

실행하면 모드를 선택합니다.

| 모드 | 설명 |
|---|---|
| `1` | 사용자 입력 모드. 3×3 필터 A, 필터 B, 패턴을 차례로 입력하면 두 점수와 판정 결과(A / B / 판정 불가), 평균 연산 시간을 출력합니다. |
| `2` | `data.json` 분석 모드. 파일 안의 모든 패턴 케이스를 판정해 PASS/FAIL을 출력하고, 마지막에 크기별 성능 표를 출력합니다. |

- 모드 2는 `data.json`이 `main.py`와 **같은 폴더**에 있어야 하며, 그 폴더에서 실행해야 합니다.
- 모드 1 입력 형식: 한 줄에 숫자 3개를 공백으로 구분해 3줄 입력합니다. 예) `0 1 0`

## 구현 요약

- **MAC 연산**: `mac(pattern, filter)`가 이중 `for` 루프로 같은 위치의 원소를 곱해 모두 더합니다. 외부 라이브러리 없이 직접 구현했습니다.
- **판정 규칙**: 두 필터 점수를 비교해 큰 쪽으로 판정합니다.
- **동점 정책**: 부동소수점 오차를 고려해 `abs(a - b) < 1e-9`이면 동점으로 봅니다. 이 비교는 `is_tie(a, b)` 함수 하나로 모아 모드 1과 모드 2가 똑같이 사용합니다. `==` 비교는 사용하지 않습니다. 모드별 처리는 아래 [모드별 동점 처리](#모드별-동점-처리)를 참고하세요.
- **라벨 정규화**: `data.json`의 정답 라벨이 여러 표기로 섞여 있어도 비교할 수 있도록 `normalize_label()`에서 `'+'`, `'cross'` → `Cross`, `'x'` → `X`로 통일합니다(대소문자·앞뒤 공백 무시).
- **필터 키 정규화**: 필터 키도 정답 라벨과 **같은 규칙**으로 맞춥니다. `normalize_filters()`가 `size_N` 아래의 키를 `normalize_label()`로 변환하므로 `cross`, `Cross`, `CROSS`, `+`는 모두 `Cross`로, `x`, `X`는 `X`로 인식됩니다. 코드는 정규화된 키 `Cross` / `X`로만 필터를 꺼내므로, 데이터의 표기가 바뀌어도 코드를 고칠 필요가 없습니다.
- **모드 1 입력 검증**: 숫자가 아니거나 한 줄의 개수가 3개가 아니면 오류 메시지를 출력하고 해당 행렬을 다시 입력받습니다. 프로그램이 종료되지 않습니다.
- **모드 2 예외 처리**: 케이스 키에서 크기 N을 읽어 `size_N` 필터를 찾습니다. 필터 키가 없거나(KeyError) 패턴 크기가 N×N이 아니면(ValueError) 그 케이스만 `FAIL`과 사유를 출력하고 다음 케이스로 넘어갑니다. 한 케이스의 문제로 전체가 중단되지 않습니다.
- **시간 측정**: `time.perf_counter()`로 MAC 연산을 10회 반복한 평균 시간(ms)을 측정합니다.

### 키 매칭 규칙 (모드 2)

| 단계 | 규칙 | 예시 |
|---|---|---|
| 1. 크기 추출 | 패턴 키를 `_`로 나눈 두 번째 값을 N으로 사용 | `size_13_2` → N = 13 |
| 2. 필터 묶음 찾기 | `filters["size_N"]` | `filters["size_13"]` |
| 3. 필터 키 정규화 | `normalize_label()`로 `Cross` / `X`로 통일 | `"cross"`, `"+"` → `Cross`, `"x"` → `X` |
| 4. 정답 라벨 정규화 | 같은 `normalize_label()` 사용 | `"+"` → `Cross` |
| 5. 크기 검증 | 패턴이 N×N이 아니면 해당 케이스만 FAIL | |

`size_N`이 없거나 정규화 후 `Cross` / `X` 키가 없으면 KeyError로 잡아 해당 케이스만 `FAIL (사유: ...)`로 출력합니다.

### 모드별 동점 처리

두 모드 모두 `is_tie(a, b)` (`abs(a - b) < 1e-9`)로 동점을 판단하지만, 비교 대상과 동점 이후의 처리가 다릅니다.

| 구분 | 모드 1 (사용자 입력) | 모드 2 (data.json 분석) |
|---|---|---|
| 비교하는 두 점수 | 필터 A 점수 vs 필터 B 점수 | Cross 필터 점수 vs X 필터 점수 |
| 동점이 아닐 때 | 큰 쪽에 따라 `A` 또는 `B` 출력 | 큰 쪽에 따라 `Cross` 또는 `X` |
| 동점일 때 | `판정 불가 (UNDECIDED)`를 출력하고 끝 (정답이 없으므로 PASS/FAIL 없음) | 판정값을 `UNDECIDED`로 정한 뒤 정답 라벨(`Cross`/`X`)과 비교 → 정답에 `UNDECIDED`는 없으므로 항상 **FAIL**, 사유로 "설계상 동점, epsilon 정책상 UNDECIDED" 출력 |

즉 모드 1에서 동점은 "결과 정보"로 사용자에게 알려주는 것이고, 모드 2에서 동점은 "정답과 다른 판정"이므로 FAIL로 집계됩니다.

### 새 라벨을 추가할 때 체크리스트

예를 들어 `Circle` 같은 새 모양을 추가하려면 아래 순서로 진행합니다.

1. [ ] **`normalize_label()` 수정**: 새 라벨의 표기들(예: `'o'`, `'circle'`)을 표준 이름 `Circle`로 바꾸는 분기를 추가합니다. 필터 키도 이 함수를 거치므로 필터 쪽은 따로 고칠 필요가 없습니다.
2. [ ] **판정 로직 확인**: `judge()`가 두 점수만 비교하므로, 세 라벨 이상을 비교하도록 "가장 큰 점수의 라벨 찾기 + 최댓값끼리 `is_tie()`면 UNDECIDED" 형태로 바꿉니다.
3. [ ] **데이터 추가**: `data.json`의 각 `size_N`에 새 필터를 추가하고, 새 라벨이 정답인 패턴 케이스를 넣습니다.
4. [ ] **테스트 케이스 추가**: 새 라벨의 여러 표기(대소문자, 기호)가 모두 같은 이름으로 정규화되는지, 새 패턴이 PASS하는지, 동점 케이스가 UNDECIDED로 나오는지 확인합니다.
5. [ ] **실행 확인**: `python3 main.py` 모드 2를 실행해 기존 케이스 결과가 바뀌지 않았는지 확인합니다.
6. [ ] **문서 수정**: README의 라벨 정규화 규칙, 키 매칭 규칙 표, 결과 리포트를 갱신합니다.

| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |

## FAIL 케이스 원인 분석

FAIL 3건(size_5_1, size_13_2, size_25_1)은 모두 판정이 `UNDECIDED`로 나와 정답과 달라진 경우입니다.
원인을 ① 데이터/스키마 문제, ② 로직 문제, ③ 수치(부동소수점) 문제로 나누어 확인했습니다.

**① 데이터/스키마: 필터 가중치가 수학적으로 동점을 만들도록 설계되어 있습니다.**

- **size_5_1** (X 패턴): 패턴이 Cross 필터와 겹치는 칸은 중앙 1칸뿐이고 그 가중치가 0.9이므로 Cross = 1 × 0.9 = **0.9**. X 필터는 대각선 9칸이 모두 0.1이므로 X = 9 × 0.1 = **0.9**. 정확히 같은 값입니다.
- **size_13_2** (Cross 패턴): Cross 필터는 가로·세로 25칸이 모두 0.3이므로 Cross = 25 × 0.3 = **7.5**. X 필터는 패턴과 겹치는 중앙 칸의 가중치가 7.5라서 X = **7.5**. 역시 같은 값입니다.
- **size_25_1** (X 패턴): Cross 필터의 중앙 가중치가 4.9이므로 Cross = **4.9**. X 필터는 대각선 49칸이 모두 0.1이므로 X = 49 × 0.1 = **4.9**. 같은 값입니다.
- 키 누락이나 크기 불일치 같은 스키마 오류는 없었습니다. 6개 케이스 모두 필터와 패턴의 키·크기가 맞아 정상적으로 MAC 연산까지 진행되었습니다.

**③ 수치: 부동소수점 덧셈 오차 때문에 "같은 값"이 다르게 표현됩니다.**

- 0.1, 0.3은 2진수로 정확히 표현되지 않기 때문에 여러 번 더하면 오차가 누적됩니다. 그 결과 0.9 → 0.8999999999999999, 7.5 → 7.499999999999997, 4.9 → 4.899999999999999처럼 수학적으로는 같은 값이 아주 조금 작게 계산됩니다.
- 만약 `==`나 단순 `>`로 비교했다면, 수학적으로 동점인데도 오차 방향에 따라 size_5_1과 size_25_1은 Cross, size_13_2는 X로 판정되었을 것입니다. 즉 데이터의 우연한 오차가 판정을 결정하게 되고, 덧셈 순서만 바꿔도 결과가 뒤집힐 수 있는 불안정한 판정이 됩니다.
- 그래서 `abs(a - b) < 1e-9`를 동점 기준으로 사용했고, 세 케이스의 차이(약 1e-16 ~ 3e-15)는 모두 이 기준 안에 들어와 `UNDECIDED`로 처리되었습니다.

**② 로직: 코드 로직에는 문제가 없습니다.**

- PASS 3건은 점수 차이가 크고(예: 52.9 vs 0.1) 정답과 정확히 일치합니다. MAC 연산과 비교 로직이 올바르게 동작한다는 뜻입니다.
- FAIL 3건도 계산된 점수 자체는 손으로 계산한 값(0.9, 7.5, 4.9)과 오차 범위 내에서 일치합니다.
- 따라서 FAIL의 원인은 **데이터 설계(의도된 동점) + 부동소수점 비교**이며, 프로그램 버그가 아닙니다.

**코드를 고쳐서 억지로 PASS를 만들지 않은 이유**

- 동점일 때 정답 쪽으로 몰아주거나 epsilon을 없애 `==` 비교로 되돌리면 이 데이터에서는 PASS가 늘어날 수 있지만, 그것은 정답을 보고 규칙을 끼워 맞추는 것입니다.
- 수학적으로 동점인 입력은 어느 한쪽으로 판정할 근거가 없으므로 `UNDECIDED`가 올바른 결과입니다. 실제 NPU에서도 오차로 인해 판정이 흔들리는 것보다 "판정 불가"를 명확히 알리는 편이 안전합니다.
- 이 FAIL들은 "부동소수점 동점을 어떻게 다루는가"를 확인하도록 데이터가 설계된 결과로 보고, 정책(epsilon)을 일관되게 유지했습니다.

## 성능 분석

모드 2 실행 시 출력되는 성능 표입니다(MAC 10회 반복 평균, 실행 환경에 따라 수치는 조금씩 달라집니다).
3×3은 `data.json`에 없어서 코드 안의 3×3 십자 패턴으로 측정했습니다.

| 크기(N×N) | 평균 시간(ms, 10회 평균) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0005 | 9 |
| 5×5 | 0.0010 | 25 |
| 13×13 | 0.0038 | 169 |
| 25×25 | 0.0133 | 625 |

- MAC 연산은 N×N의 모든 칸을 한 번씩 곱하고 더하므로 곱셈·덧셈 횟수가 N²이고, 시간 복잡도는 **O(N²)**입니다.
- 3×3 → 25×25에서 연산 횟수는 625 / 9 ≈ **69배** 늘었지만, 측정 시간은 0.0133 / 0.0005 ≈ **27배** 정도 늘었습니다.
- 시간 증가율이 연산 횟수 증가율보다 작은 이유는 함수 호출, 루프 준비, `perf_counter` 호출 같은 **N과 무관한 고정 비용**이 작은 N에서 상대적으로 크게 차지하기 때문입니다. N이 커질수록 고정 비용의 비중이 줄어 시간 증가가 N²에 가까워집니다(13×13 → 25×25: 연산 3.7배, 시간 약 3.5배).
- 측정 시간이 마이크로초 단위로 매우 짧아 실행할 때마다 값이 조금씩 흔들리므로, 10회 평균으로 측정했습니다.

### 큰 N을 위한 최적화 전략

현재 구현은 과제 조건(표준 라이브러리, 이중 루프)에 맞춘 것이고, N이 훨씬 커지면 다음 방법을 고려할 수 있습니다.

1. **1차원 평탄화와 메모리 지역성**: 2차원 리스트 `pattern[i][j]`는 행마다 별도 리스트를 따라가야 합니다. 행렬을 길이 N²의 1차원 배열로 펴서 연속된 메모리를 순서대로 읽으면 캐시 적중률이 높아지고, 인덱스 계산도 `i * N + j` 하나로 줄어듭니다. 파이썬에서는 `sum(a * b for a, b in zip(p_flat, f_flat))`처럼 쓰면 루프 오버헤드도 줄어듭니다.
2. **블로킹/타일링**: 큰 행렬을 캐시에 들어가는 작은 블록(예: 32×32)으로 나눠 블록 단위로 계산합니다. 한 번 캐시에 올린 데이터를 최대한 재사용해 메모리 접근 비용을 줄입니다. 여러 필터를 같은 패턴에 적용할 때 특히 효과가 큽니다.
3. **병렬화**: MAC은 각 칸의 곱셈이 서로 독립이라 나눠서 계산한 뒤 부분합을 더하면 됩니다. 행 단위로 나눠 `multiprocessing`으로 여러 코어에 분배하거나, 여러 케이스·여러 필터를 동시에 처리할 수 있습니다. (파이썬 스레드는 GIL 때문에 CPU 연산 병렬화 효과가 작아 프로세스를 사용합니다.)
4. **언어 수준 개선**: 파이썬 인터프리터의 반복 오버헤드가 가장 큰 비용입니다. 핵심 MAC 루프를 C 확장 모듈, Cython, 또는 NumPy(내부가 C와 SIMD로 구현됨)로 옮기면 수십~수백 배 빨라질 수 있습니다. 표준 라이브러리 안에서는 `array` 모듈로 숫자를 연속 메모리에 저장하는 정도가 가능합니다.
5. **부동소수점 누적 오차 완화**: N이 커질수록 덧셈 횟수가 늘어 오차도 커지므로, `math.fsum()` 같은 보정 합산을 쓰면 동점 판정이 더 안정적입니다(성능은 약간 손해).

### CPU 직렬 처리 vs NPU 병렬 처리

| 구분 | CPU (현재 구현) | NPU (MAC 어레이) |
|---|---|---|
| 처리 방식 | 곱셈 1번 + 덧셈 1번을 N²번 **차례로** 반복 | 수많은 MAC 유닛이 곱셈을 **동시에** 수행하고, 덧셈 트리로 한 번에 합산 |
| 25×25 연산 | 625번의 곱셈·덧셈을 순서대로 실행 | MAC 유닛이 625개 이상이면 곱셈은 1단계, 합산은 약 log₂625 ≈ 10단계 |
| 시간 증가 | N²에 비례 (O(N²)) | 유닛 수 안에서는 거의 일정, 넘으면 타일로 나눠 반복 |
| 강점 | 범용성, 분기·제어가 많은 작업 | 같은 형태의 곱셈-누적이 대량으로 반복되는 작업 (합성곱, 행렬 곱) |

**NPU에서 예상되는 병목**

- **메모리 대역폭**: 연산 유닛은 매우 빠르지만 패턴과 필터 값을 메모리에서 가져오는 속도가 따라가지 못하면 유닛이 데이터를 기다리며 놉니다. 그래서 NPU는 칩 안에 작은 고속 버퍼(SRAM)를 두고 필터 가중치를 재사용합니다.
- **데이터 전송 비용**: CPU 메모리에서 NPU로 데이터를 옮기는 시간이 있어, 이 과제처럼 작은 행렬 하나를 계산할 때는 전송 시간이 연산 시간보다 커서 오히려 CPU가 빠를 수 있습니다. NPU는 데이터를 한 번 보내고 많은 연산을 하는 큰 작업에서 이득을 봅니다.
- **크기 불일치와 활용률**: MAC 어레이 크기(예: 16×16)에 N이 딱 맞지 않으면 남는 유닛이 생겨 효율이 떨어집니다(예: 25×25를 16×16 타일로 나누면 마지막 타일 일부가 빈 채로 계산됨).
- **정밀도**: NPU는 속도와 전력을 위해 FP16, INT8 같은 낮은 정밀도를 많이 씁니다. 이 경우 오차가 더 커지므로, 이 과제의 동점 케이스처럼 epsilon 기준을 정밀도에 맞게 다시 정해야 합니다.
