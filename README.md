# E1-3 Mini NPU 시뮬레이터

패턴(N×N)과 필터를 MAC(Multiply-Accumulate) 연산으로 비교해 십자(Cross)와 X 중 어느 모양인지 판정하는 간단한 NPU 시뮬레이터입니다.
Python 3.8 이상, 표준 라이브러리만 사용합니다(NumPy 등 외부 라이브러리 없음).

## 실행 방법

```bash
python3 main.py
```

실행하면 모드를 선택합니다.

| 모드 | 설명 |
|---|---|
| `1` | 사용자 입력 모드. 3×3 필터 A, 필터 B, 패턴을 차례로 입력하면 두 점수와 판정 결과(A / B / 판정 불가), 평균 연산 시간을 출력합니다. |
| `2` | `data.json` 분석 모드. 파일 안의 모든 패턴 케이스를 판정해 PASS/FAIL을 출력하고, 마지막에 크기별 성능 표를 출력합니다. |

- 모드 2는 `data.json`이 `main.py`와 **같은 폴더**에 있어야 하며, 그 폴더에서 실행해야 합니다.
- 모드 1 입력 형식: 한 줄에 숫자 3개를 공백으로 구분해 3줄 입력합니다. 예) `0 1 0`

## 구현 요약

- **MAC 연산**: `mac(pattern, filter)`가 이중 `for` 루프로 같은 위치의 원소를 곱해 모두 더합니다. 외부 라이브러리 없이 직접 구현했습니다.
- **판정 규칙**: Cross 필터 점수와 X 필터 점수를 비교해 큰 쪽으로 판정합니다.
- **동점 정책**: 부동소수점 오차를 고려해 `abs(a - b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(판정 불가)로 처리합니다. `==` 비교는 사용하지 않습니다.
- **라벨 정규화**: `data.json`의 정답 라벨이 여러 표기로 섞여 있어도 비교할 수 있도록 `'+'`, `'cross'` → `Cross`, `'x'` → `X`로 통일합니다(대소문자·공백 무시).
- **모드 1 입력 검증**: 숫자가 아니거나 한 줄의 개수가 3개가 아니면 오류 메시지를 출력하고 해당 행렬을 다시 입력받습니다. 프로그램이 종료되지 않습니다.
- **모드 2 예외 처리**: 케이스 키에서 크기 N을 읽어 `size_N` 필터를 찾습니다. 필터 키가 없거나(KeyError) 패턴 크기가 N×N이 아니면(ValueError) 그 케이스만 `FAIL`과 사유를 출력하고 다음 케이스로 넘어갑니다. 한 케이스의 문제로 전체가 중단되지 않습니다.
- **시간 측정**: `time.perf_counter()`로 MAC 연산을 10회 반복한 평균 시간(ms)을 측정합니다.

## 결과 리포트

모드 2 실제 실행 결과입니다.

```

1. 사용자 입력 (3×3)
2. data.json 분석
모드를 선택하세요 (1/2): 2
[size_5_1] Cross: 0.9, X: 0.8999999999999999 → 판정 UNDECIDED / 정답 X → FAIL (사유: 필터 가중치로 인한 설계상 동점, epsilon 정책상 UNDECIDED)
[size_5_2] Cross: 8.9, X: 0.1 → 판정 Cross / 정답 Cross → PASS
[size_13_1] Cross: 0.3, X: 14.700000000000008 → 판정 X / 정답 X → PASS
[size_13_2] Cross: 7.499999999999997, X: 7.5 → 판정 UNDECIDED / 정답 Cross → FAIL (사유: 필터 가중치로 인한 설계상 동점, epsilon 정책상 UNDECIDED)
[size_25_1] Cross: 4.9, X: 4.899999999999999 → 판정 UNDECIDED / 정답 X → FAIL (사유: 필터 가중치로 인한 설계상 동점, epsilon 정책상 UNDECIDED)
[size_25_2] Cross: 52.9, X: 0.1 → 판정 Cross / 정답 Cross → PASS

총 6개 중 3개 PASS, 3개 FAIL
```

| 케이스 | Cross 점수 | X 점수 | 판정 | 정답 | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

## FAIL 케이스 원인 분석

FAIL 3건(size_5_1, size_13_2, size_25_1)은 모두 판정이 `UNDECIDED`로 나와 정답과 달라진 경우입니다.
원인을 ① 데이터/스키마 문제, ② 로직 문제, ③ 수치(부동소수점) 문제로 나누어 확인했습니다.

**① 데이터/스키마: 필터 가중치가 수학적으로 동점을 만들도록 설계되어 있습니다.**

- **size_5_1** (X 패턴): 패턴이 Cross 필터와 겹치는 칸은 중앙 1칸뿐이고 그 가중치가 0.9이므로 Cross = 1 × 0.9 = **0.9**. X 필터는 대각선 9칸이 모두 0.1이므로 X = 9 × 0.1 = **0.9**. 정확히 같은 값입니다.
- **size_13_2** (Cross 패턴): Cross 필터는 가로·세로 25칸이 모두 0.3이므로 Cross = 25 × 0.3 = **7.5**. X 필터는 패턴과 겹치는 중앙 칸의 가중치가 7.5라서 X = **7.5**. 역시 같은 값입니다.
- **size_25_1** (X 패턴): Cross 필터의 중앙 가중치가 4.9이므로 Cross = **4.9**. X 필터는 대각선 49칸이 모두 0.1이므로 X = 49 × 0.1 = **4.9**. 같은 값입니다.
- 키 누락이나 크기 불일치 같은 스키마 오류는 없었습니다. 6개 케이스 모두 필터와 패턴의 키·크기가 맞아 정상적으로 MAC 연산까지 진행되었습니다.

**③ 수치: 부동소수점 덧셈 오차 때문에 "같은 값"이 다르게 표현됩니다.**

- 0.1, 0.3은 2진수로 정확히 표현되지 않기 때문에 여러 번 더하면 오차가 누적됩니다. 그 결과 0.9 → 0.8999999999999999, 7.5 → 7.499999999999997, 4.9 → 4.899999999999999처럼 수학적으로는 같은 값이 아주 조금 작게 계산됩니다.
- 만약 `==`나 단순 `>`로 비교했다면, 수학적으로 동점인데도 오차 방향에 따라 size_5_1과 size_25_1은 Cross, size_13_2는 X로 판정되었을 것입니다. 즉 데이터의 우연한 오차가 판정을 결정하게 되고, 덧셈 순서만 바꿔도 결과가 뒤집힐 수 있는 불안정한 판정이 됩니다.
- 그래서 `abs(a - b) < 1e-9`를 동점 기준으로 사용했고, 세 케이스의 차이(약 1e-16 ~ 3e-15)는 모두 이 기준 안에 들어와 `UNDECIDED`로 처리되었습니다.

**② 로직: 코드 로직에는 문제가 없습니다.**

- PASS 3건은 점수 차이가 크고(예: 52.9 vs 0.1) 정답과 정확히 일치합니다. MAC 연산과 비교 로직이 올바르게 동작한다는 뜻입니다.
- FAIL 3건도 계산된 점수 자체는 손으로 계산한 값(0.9, 7.5, 4.9)과 오차 범위 내에서 일치합니다.
- 따라서 FAIL의 원인은 **데이터 설계(의도된 동점) + 부동소수점 비교**이며, 프로그램 버그가 아닙니다.

**코드를 고쳐서 억지로 PASS를 만들지 않은 이유**

- 동점일 때 정답 쪽으로 몰아주거나 epsilon을 없애 `==` 비교로 되돌리면 이 데이터에서는 PASS가 늘어날 수 있지만, 그것은 정답을 보고 규칙을 끼워 맞추는 것입니다.
- 수학적으로 동점인 입력은 어느 한쪽으로 판정할 근거가 없으므로 `UNDECIDED`가 올바른 결과입니다. 실제 NPU에서도 오차로 인해 판정이 흔들리는 것보다 "판정 불가"를 명확히 알리는 편이 안전합니다.
- 이 FAIL들은 "부동소수점 동점을 어떻게 다루는가"를 확인하도록 데이터가 설계된 결과로 보고, 정책(epsilon)을 일관되게 유지했습니다.

## 성능 분석

모드 2 실행 시 출력되는 성능 표입니다(MAC 10회 반복 평균, 실행 환경에 따라 수치는 조금씩 달라집니다).
3×3은 `data.json`에 없어서 코드 안의 3×3 십자 패턴으로 측정했습니다.

| 크기(N×N) | 평균 시간(ms, 10회 평균) | 연산 횟수(N²) |
|---|---|---|
| 3×3 | 0.0005 | 9 |
| 5×5 | 0.0010 | 25 |
| 13×13 | 0.0038 | 169 |
| 25×25 | 0.0133 | 625 |

- MAC 연산은 N×N의 모든 칸을 한 번씩 곱하고 더하므로 곱셈·덧셈 횟수가 N²이고, 시간 복잡도는 **O(N²)**입니다.
- 3×3 → 25×25에서 연산 횟수는 625 / 9 ≈ **69배** 늘었지만, 측정 시간은 0.0133 / 0.0005 ≈ **27배** 정도 늘었습니다.
- 시간 증가율이 연산 횟수 증가율보다 작은 이유는 함수 호출, 루프 준비, `perf_counter` 호출 같은 **N과 무관한 고정 비용**이 작은 N에서 상대적으로 크게 차지하기 때문입니다. N이 커질수록 고정 비용의 비중이 줄어 시간 증가가 N²에 가까워집니다(13×13 → 25×25: 연산 3.7배, 시간 약 3.5배).
- 측정 시간이 마이크로초 단위로 매우 짧아 실행할 때마다 값이 조금씩 흔들리므로, 10회 평균으로 측정했습니다.
